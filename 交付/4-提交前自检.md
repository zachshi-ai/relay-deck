## 八、怎么发布（三条路，坑不一样）

先说结论：**这份材料本身就是"链接自洽"的**——`node scripts/check-delivery.mjs` 与
`node scripts/check-fresh-clone.mjs` 会验证每一处相对链接和引用是否真的存在。
所以**在哪发布，决定了这些链接会不会失效**。

### 路线 A（推荐，最省事）：推到公开的 Git 仓库

```bash
cd relay-deck
git remote add origin <你的公开仓库地址>
git push -u origin main
```

- **作品链接**就用仓库地址（或仓库里 `交付/1-作业正文.md` 的网页地址）。
- 优点：**图片与所有相对链接都直接可用**（它们本来就是仓库内相对路径），
  仓库只有 110 个文件 / 约 1.9 MB；`.gitignore` 已经把本地数据、日志、编译产物排除掉了。
- 评审点进去就能顺着链接查到每一个证据文件——这是最能体现"证据可复查"的方式。

### 路线 B：飞书文档（需要手动补两样东西）

导入 Markdown 之后有两处必须手工处理：

1. **图片**：正文 §0 里嵌的那张界面图不会自己上传，需要手动插入。
   本作业一共用到这些图（都在 `evidence/` 下）：
   - `ui-stage3.png` —— 四 Agent + 会话 + 用量 + 板级 LED 真值表（正文 §0 用）
   - `ui-recovery.png` —— "上下文已重置"标记（可选）
   - `ui-stage1.5.png` —— 会话隔离/搜索/接力链上线时（可选）
2. **相对链接**：正文里指向 `evidence/` 下证据文件、以及 `docs/` 下文档的那些相对链接，在飞书里点了会 404。
   两种处理都行：① 把「§5.2 证据矩阵」当成"随附文件清单"，把文件名保留为纯文本；
   ② 如果同时也推了 Git 仓库，就把这些链接换成仓库地址。

### 路线 C：只交正文 + 一个外部链接

如果单位/平台只收一个链接，就用路线 A 的仓库地址，正文直接看仓库里的文件。

### 附：可直接粘贴的「作品简介」（约 150 字）

> **RelayDeck 接力台**：一块 8 键 + 1 旋钮的 EasyInput 硬件键盘，驱动一个把多个 AI Agent
> 接在一起的中台。它把四个真实可用的 Agent（DeepSeek Harness / Codex / MiniMax / Kimi）

> 上下文从此不需要鼠标。全部代码零第三方依赖，127 项单测 + 覆盖率 98.2%，验收脚本可复跑。
