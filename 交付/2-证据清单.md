## 二、跨 Agent 接力验收（三组，各 11/11）

```bash
node scripts/e2e-http.mjs dsh codex      # → evidence/http-e2e-2026-10-07T14-01-56-213Z.json
node scripts/e2e-http.mjs dsh minimax    # → evidence/http-e2e-2026-10-07T13-55-20-177Z.json
node scripts/e2e-http.mjs dsh kimi       # → evidence/http-e2e-2026-10-07T13-57-24-542Z.json
```

每组 11 项检查，关键三项：

1. 上游答出"已记住 42"；
2. 下游（自己会话里没有 42）**靠接力上下文答出 42**；
3. 对没有续跑能力的 Agent，**不给接力上下文**再问一轮，靠中台补的历史仍然答对（有续跑能力的 Agent 此项标记为"跳过"）。

同时验证：会话隔离（两个会话的续跑线不同）、消息不跨会话、搜索命中、接力链可回溯、用量有记录。

## 五、续跑线失效自愈（7/7）

```bash
node scripts/e2e-session-recovery.mjs    # → evidence/session-recovery-2026-10-07T14-05-56-170Z.json
```

脚本**自己制造故障**：正常跑一轮拿到真实续跑线 → 把数据文件里这条线改成一个不存在的 session（模拟会话过期/被删/换机器）→ 调 `POST /api/admin/reload` 让改动生效 → 再发一轮。

| 检查 | 结果 |
| --- | --- |
| 第 1 轮正常建立续跑线 | ✅ |
| 故障已注入（内存里确实是坏 session） | ✅ `session-nonexistent-…` |
| **坏 session 下仍然成功产出** | ✅ 自愈生效 |
| 如实上报 `contextReset` | ✅ 用户能看到"上下文已重置" |
| 重试只有一次 | ✅ `attempts=2` |
| 坏线被替换成新线 | ✅ |
| 后续轮次恢复正常（不再重置） | ✅ `attempts=1` |

修复前的行为（实测记录）：每一轮都返回 `session "…" does not exist; omit --session-id to start a new Session`，**永久失败且无法自愈**。

## 十三、实板实测（2026-10-07，USB 直连）

工具：`tools/hidtool.swift`（IOKit HID，零依赖）

```bash
swiftc -O tools/hidtool.swift -o tools/hidtool
./tools/hidtool list          # 设备身份
./tools/hidtool diagnose      # 逐个 report 试读写
./tools/hidtool agent-sweep   # 肉眼确认用：暗蓝 → 红 → 绿 → 琥珀 → 熄灭
```

| 检查 | 结果 |
| --- | --- |
| 设备身份 | ✅ `EasyInput AI`，VID `0x303A` / PID `0x1006`，序列号 `easy-input-v2` |
| HID 接口 | ✅ 1 个接口，usagePage `0x1` / usage `0x6`，`maxFeature=64`，描述符 250 字节 |
| Feature 写通路 | ✅ `SetReport(0x12/0x13/0x10)` 全部返回 `0x00000000` |
| 五色灯序下发 | ✅ 5 帧全部被 USB 栈接受（纪元序号） |
| **中台 → 板子 回路** | ✅ 服务日志：`Idle → Running → CompletedUnread` 三次推送，`SetReport` 全部成功 |
| **灯是否真的亮起** | ❓ **只能肉眼确认**——固件 `GET_REPORT` 未实现、无串口日志 |
| 真机按键 | ⏳ 未测（另需「输入监控」权限才能读输入报告） |

**三个必须记住的坑**（详见 [阶段2b 实测记录](../docs/hardware-stage2b.md)）：

1. 只调 `IOHIDManagerOpen` 时 `SetReport` 返回 `0xe00002cd`，**必须对设备显式 `IOHIDDeviceOpen`**；
2. 固件 `tud_hid_get_report_cb` 是空实现 → **不存在"读回 Agent 状态"这条路**，读回全零不代表失败；
3. 读输入报告需要 macOS **「输入监控」权限**，缺它时回调一条都不触发。

**关键约束**：固件在 **BLE 与 USB 同一轮都挂着待处理帧**时按序号仲裁
（`agent_status_sequence_is_newer`），输的那一帧被丢弃；只有单一路来源时一定生效
（`take_pending_agent_status` 是消费型的）。中台已改为从**纪元**起算序号，
让自己天生赢下这个窄窗口，而不是从 0 起算。

## 十五、没有证据的部分（如实列出）

- **实板点灯的最终确认**：主机侧写入通路已验证，但"灯真的亮了"没有任何可读回证据，只能肉眼确认（命令已备好）。
- **真机按键 → 中台**：未测；除物理按键外还需给终端「输入监控」权限。
- **ZCode**：没有成功记录，只有失败排查过程（见 [Agent 接入手册](../docs/agent-onboarding.md)）。
- **弱网（高丢包/高延迟）**：没有真实构造。目前只覆盖了"子进程超时被终止"与"二进制不存在"这两种失败路径。
- **多用户与鉴权**：没有，中台只监听 127.0.0.1。
