# 第 8 课毕业大作业 · RelayDeck 接力台

> **作品链接（指南唯一硬指标）**：`【待填 —— 把本文上传成飞书文档，把公开链接粘到这里】`
>
> **方向**：**方向二「从零开始实现自己想做的一个项目」为主**；同时在 EasyInput 现有工程上做了功能延伸，**因此也覆盖方向一**。
>
> **一句话**：一块 8 键 + 1 旋钮的硬件键盘，驱动一个把多个 AI Agent 接在一起的中台——切人、接力、定位、复制、拉群，手不离键盘。

---

## 0. 三十秒看懂

我有四个 AI Agent 每天在用（DeepSeek Harness、Codex、MiniMax、Kimi），但它们的会话是互相隔离的孤岛：想把 A 的答案交给 B 接着做，只能鼠标选中 → 复制 → 切窗口 → 粘贴；想回到"之前某一句"追问，只能在长对话里翻。

**RelayDeck 做的就是这一件事**：一个中台把这些 Agent 接进来，用一套统一的焦点句模型串起来，再把「选择 + 发送」这两个动作从屏幕上搬到硬件键盘上。

```
选中某句回答  ──按 S2──►  接力给第 2 个 Agent（带着这句作为引用上下文）
旋钮转        ──►  在消息流里上下移动焦点（只看，不发送）
按 S7        ──►  复制焦点句
按 S8        ──►  把问题广播给全部 Agent，再由主持人汇总共识/分歧
```

**证据**：四个 Agent 全部真实跑通；跨 Agent 接力验收 **11/11**；边界验证 **10/10**；单元测试 **61 项**。截图见 [evidence/ui-stage3.png](../evidence/ui-stage3.png)。

## 1. 第一步 · 提出想法：我到底要解决什么

摘要是三句话：

1. **给谁用**：我自己——每天要在多个 Agent 之间搬运上下文的人。
2. **解决什么**：切换与搬运的成本。切换 Agent 要切窗口；搬运上下文要选中复制；想引用某一句要在长对话里翻找。
3. **为什么值得用硬件做**：这三个动作的本质都是"选择 + 发送"。**它们本来就该闭着眼睛用手完成**，而不是在屏幕上找按钮。这是我用它而不是再写一个网页插件的理由。

做完之后我一直用的一条真实路径：让 DeepSeek Harness 先给方案，按一下 `S2` 把它整段丢给 Codex 要求"照着这个改代码"，再按 `S3` 让 MiniMax 用一句话反驳它——**三次按键，零次复制粘贴**。

## 2. 第二步 · 方案与选型

### 2.1 三条接入路径，为什么选了 CLI 无头

| 路径 | 做法 | 结论 |
| --- | --- | --- |
| **CLI 无头**（选中） | `dsh --profile headless --json`、`codex exec --json`、`mmx text chat`、`kimi-daimon --prompt` | 有官方入口、能拿到结构化输出、能续跑会话、可脚本化 |
| GUI 自动化 | AppleScript 抄屏 / 模拟点击 | 脆、要前台、拿不到结构化输出——**放弃** |
| 私有端口 API | ZCode 的 61923、Kimi 的 49328 | 试了常见路径全 404 / 401，**没有公开协议，放弃**（详见 [Agent 接入手册](../docs/agent-onboarding.md)） |

### 2.2 四个 Agent 的差异，为什么必须一个 Agent 一个适配器

| Agent | 输出形态 | 会话续跑 | 特殊坑 |
| --- | --- | --- | --- |
| DeepSeek Harness | NDJSON（行分隔流） | ✅ `--session-id` | CLI 不在 PATH，在 App 包内 |
| Codex | JSONL（行分隔流） | ✅ `exec resume` | `resume` 子命令**不接受** `--sandbox`/`-C`；非 git 目录拒跑；stdin 不关会挂住 |
| MiniMax | **一个跨多行的 JSON 对象** | ❌ | `--messages-file -` 只认裸数组，写成 `{"messages":[...]}` 会报 `s is not iterable` |
| Kimi | **日志与回答混在同一个 stdout** | ❌ | 正文必须走 argv（stdin 是它的控制命令通道）；必须显式指 `DAIMON_CONFIG_PATH`；持有 `runner.lock` 不能并发 |

结论：**"统一事件模型"是设计出来的，不是自然存在的**。适配器吃掉差异，核心只认 `text / thinking / usage / error / final / turn.end`。这也是为什么新增一个 Agent 只需要加一个文件。

### 2.3 三个关键设计取舍

**① 按键 = 发送，旋钮 = 查看。** 需求里其实藏着两个焦点：焦点在"人"（切 Agent 接力）和焦点在"句"（定位某句话）。我把它们彻底分开——按 1–5 就是**发出去**，转旋钮就是**只看不动**。这样就不需要"先按哪个再按哪个"，也就绕开了指南里说的「避免两级菜单」。

**② 接力用引用，不用全量历史。** 全量会爆 token，摘要会丢细节。所以接力只带三样：**被选中的那一句 + 上游结论 + 原始问题**，每段都有长度上限。

**③ 没有续跑能力的 Agent，由中台补历史。** MiniMax、Kimi 都是一次性调用，自己记不住上一轮。中台在它们上场的轮次注入一段有上限的历史——**并且这条兜底是被验证过的**：第三轮故意不给接力上下文，它仍然答对了。

## 3. 第三步 · 材料与环境准备

| 项 | 内容 |
| --- | --- |
| 硬件 | EasyInput V2（ESP32-S3，8 键 + 旋钮 + 5×WS2812 + 麦克风 + 扬声器 + 电池） |
| 固件基线 | `easy-input-maker`（公开基线，ESP-IDF 5.5.5） |
| 运行环境 | Node.js v24.18.0，零第三方依赖 |
| 已接入的 Agent | 四家 CLI 的登录态（`codex login status` / `mmx auth status` / daimon 共享配置） |

**把资料喂给 AI（这一步我按课程做了）**：板子的 [引脚表](../../easyinput-board-cy/references/pinout.md) 与 [电源与外设合同](../../easyinput-board-cy/references/power-and-peripherals.md) 是我做硬件那一半时的唯一真相源——GPIO8 是 LED/麦克风/扬声器的**共享电源域**、5 颗 WS2812 是**一条数据线**（GPIO12）、`KEY1~KEY9` 经二极管 OR 汇总到 `KEY_WAKE`。这些结论直接决定了 LED 真值表只能有 5 颗灯、以及"位置承载身份"的编码方式。

**边界纪律**：改固件时遵守 `easy-input-maker/AGENTS.md`——不提交真实 Wi-Fi 凭据与设备标识、不擅自改 GPIO/BOOT/分区/GPIO8 电源时序、构建通过/测试通过/烧录成功/实板正常四类证据分开报告。

## 5. 第五步 · 调试与验证

### 5.1 九条来自实测的硬约束（每条都是踩出来的）

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 明明失败，退出码却是 `0` | 两个 CLI 都不把失败反映到退出码 | 判失败靠"是否有文本 + 是否出现致命错误 + stderr" |
| 2 | 一次正确回答被判成失败 | Codex 先抛 `Under-development features enabled` 条目级 error | 区分 `fatal`：条目级算警告，只有 `turn.failed` 才算失败 |
| 3 | 续跑参数报错 | `codex exec resume` 不接受 `--sandbox`/`-C`，选项还必须在会话 id 之前 | 为 resume 单独构造参数 |
| 4 | 换话题后上下文串了 | 续跑线只按 Agent 存了一个 | 改成按「会话 × Agent」隔离 |
| 5 | 主持人自己的那轮消失了 | 去重按"身份"判断，而主持人常常同时是参与者 | 改成按**轮次阶段**去重 + 回归测试 |
| 6 | 接力跑完下游答非所问（MiniMax） | 它根本没有会话 | 中台注入有上限的历史（且验证过） |
| 7 | 历史超限时最近一轮丢了 | 正序拼接后整体截断，丢的是最新的 | 改成**从最新往回装**，丢最老的 |
| 8 | 配错路径却毫无提示 | 显式环境变量不存在时静默回退到 PATH | 显式覆盖优先，配错就大声失败 |
| 9 | 二进制不存在时错误信息是"没有输出" | 启动错误被适配器的空输出错误盖住 | 错误优先级：启动失败 > 超时 > 适配器报错 |

### 5.2 证据矩阵

| 验证项 | 结果 | 证据文件 |
| --- | --- | --- |
| 单元测试 | **61 项全绿**（parsers / runner / core / store / hardware / queue / 四个适配器） | `node --test` |
| 跨 Agent 接力（dsh→codex / →minimax / →kimi） | **11/11 × 3** | [http-e2e](../evidence/) |
| 4 个异构 Agent 圆桌 + 主持人汇总 | 四方全绿，产出共识/分歧/建议 | [roundtable-4agents](../evidence/roundtable-4agents-20261007T215742.sse) |
| 边界验证（坏焦点/未绑定输入/未知 Agent/坏会话/spawn 失败/超时/同 Agent 并发） | **10/10** | [boundary-2026-10-07T14-01-05-800Z.json](../evidence/boundary-2026-10-07T14-01-05-800Z.json) |
| 重启恢复 | 重启前后状态**完全一致**，8 条续跑线在盘上 | 见本文件 §5.3 |
| 硬件命令链路 | 按 S1 → LED 采样 **15 次 running / 182 次 ok** | `bin/simulate.mjs` |
| 全局热键守护进程 | 编译通过，`--selftest` 四个动作全部 ✓ | `tools/hotkeyd.swift` |

**最有说服力的一条**：让 `codex`（或 minimax / kimi）回答一个它自己的会话里**从未出现过**的数字。上游 `dsh` 先答出"已记住 42"，再把这句话作为引用上下文接力给下游——**下游答出 42**，说明接力上下文确实送达，不是模型猜的。对没有续跑能力的两个 Agent，还会多验一轮：**不给接力上下文**再问一次，靠中台补的历史答对。

### 5.3 重启恢复的验证方式

```bash
curl -s localhost:8787/api/state > before.json   # 会话数/消息数/续跑线
# 杀掉中台进程再启动
curl -s localhost:8787/api/state > after.json
diff before.json after.json                       # 无差异
```
